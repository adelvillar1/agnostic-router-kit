# Plan: the run API — applications spawn and steer workflow runs over the router's wire

**Goal:** the router's wire grows from model access for any client to run access for any application. An app points at the same local service, spawns a workflow run carrying facts, grants and answers, watches its events on the stream that already exists, answers escalations while the run is live, and collects the deliverable — under per-app tokens whose grant ceilings the plane enforces like every other capability, with the journal recording who asked.

**zcode-router-kit port:** deliberately out of scope here — its own follow-up plan, per the engine-upstream/port-discipline.

## Context (all verified in session before drafting)

- The wire was model-shaped or operator-shaped: `/v1/chat/completions` for any client, and read-only operator routes over a 1s journal watcher. `wfStart()` was the watcher bootstrapper, not a spawner — no POST touched run state.
- The spawn path existed in full: `runWorkflow(file, opts)` (engine.mjs) took args, workdir, model, grants, allowCommands, answers, onEvent; `freeRunDir` made same-second runs collision-safe; artifacts versioned under `runDir/artifacts`; `answerEscalation` resolved topics deterministically against a pre-supplied table with no live channel.
- server.js already imported the plane as a package, so a handler could call `runWorkflow` in-process and every existing surface would pick the run up from the journal unchanged.
- Judgment law (control-plane C6): plane judgments route dev-decisions first, sys1 behind it. The run API adds callers, not a side door.

## Approach

### Phase A — the plane grows two surfaces (engine-owned, verbatim-portable) — ✅ done

1. **Live answers.** `answerEscalation` gained a deterministic lookup after the spawn-time `opts.answers`: `<runDir>/answers.jsonl`, appended by the wire while the run is live (rows `{topic, answer, app, t}`). Precedence: declared topic, live topic, declared substring, live substring, `askOwner`, no-owner — and the resolution journals its source (`declared` | `live` | `owner` | `none`) through `opts.onSource`. A file read at fire time; no model, no socket in the engine. **Done 2026-10-06** — probe asserts all four sources; a declared answer demonstrably outranks a live post on the same topic.
2. **Caller provenance.** `runWorkflow` accepts `opts.app`; the run-start journal line and `summary.json` carry it; operator spawns record `app: "cli"`. **Done 2026-10-06** — probe asserts journal, summary, and dashboard-visible fields.
3. **The workflow's own `escalate`.** Added while building the zero-model fixture: only agents could escalate (tool) and asks at their cap (stuck policy) — a workflow itself had no escalation path, and C3's fixture needed one without a model call. The agent tool, the stuck policy, and the new surface-level `escalate(question, evidence, topic)` now share one `escalateToOwner` helper, so every resolution carries its source no matter who asked.

### Phase B — the wire (router/server.js, inside the existing bearer gate) — ✅ done

4. **App registry.** `roster.router.apps: [{name, token, grantCeiling, workdir?}]`; render.mjs renders app tokens into config.json beside `localToken`; `validateRoster` checks name + token + ceiling shape. The bearer gate resolves two token classes (`caller = {operator} | {app}`); the SSE route's `?token=` check accepts both; unknown → 401 as always. **Done.**
5. **`POST /v1/runs`.** Validates workflow existence, args against the workflow's own header (`parseHeader`/`validateArgs` pulled forward from the engine — a bad spawn is a 400, not a runId whose run never came to exist), facts (kind + text, engine re-validates), answers shape, and grant resolution before anything runs; enforces the ceiling (refused by name, journaled as `run-spawn-refused` in the router log); resolves the workdir inside the app's root (default `<kit home>/apps/<name>/workspaces`), refusing outside paths by name; computes `outDir` via `freeRunDir` so the response hands back `{runId, runDir}` before the run exists; runs `runWorkflow` in-process. **Done.**
6. **`POST /v1/runs/<id>/answers`** appends to the run's `answers.jsonl`, scoped to the spawning app or the operator, ownership re-derived from the journal after a restart. **Done.**
7. **`GET /v1/runs/<id>/artifacts`** lists the versioned index and downloads `?file=` inside the run directory with a traversal guard; app tokens read only their own runs' artifacts. **Done.**
8. **The read surface the operator already had is unchanged** and documented as the run-read surface. **Done.**

### Phase C — probes — ✅ done

9. **`workflows/http-probe.ts`** — zero-model-call fixture: one phase, a warmup escalation (resolves `none`), the real escalation on the spawn's topic, one markdown artifact. **Done.**
10. **`tools/probe-run-api.mjs`** — renders a scratch runtime via the kit's own pipeline, launches it on 8399 with its own `AGNOSTIC_ROUTER_KIT_HOME`, asserts the contract in 33 checks. **Done — 33/33 green.**

## Use cases (verified through the probe)

- [x] A: an application spawns a run with facts and grants over the wire, watches its events, reads the deliverable — no shell, no dashboard. *(verified 2026-10-06: operator + app spawns complete end to end, artifacts retrieved over HTTP)*
- [x] B: a run hits a blocking ambiguity mid-flight; the app answers the escalation over the wire; the journal names the source. *(verified: `source: live`, `source: declared`, `source: none` all journaled; declared beats live on the same topic)*
- [x] C: an operator audits app activity: provenance on every run; ceiling overreach is a refused spawn naming the grant. *(verified: `run-start.app`, `summary.app`, `run-spawn-refused` router-log line)*
- [x] D: two apps spawn side by side; distinct run dirs, both streamed with attribution; neither reaches the other's artifacts or answers. *(verified: same-second spawns, SSE attribution, cross-app 403s)*

## Acceptance criteria

- [x] **C1:** ceiling enforcement is code: an app requesting a grant outside its ceiling is refused by name (`out of bounds: process is not in probe-app's ceiling`), journaled; the operator token has no ceiling. *(probe C1)*
- [x] **C2:** workdir sandboxing is code: a body workdir resolving outside the app's root is refused by name; the default per-app workdir is created on demand (run-start `workdir` under `<home>/apps/<app>/workspaces`). *(probe C2 + C3 section)*
- [x] **C3:** live answering: the probe run escalates mid-run; a matching-topic POST resolves it (journal source: `live`); a declared answer outranks a live one for the same topic (`source: declared`); the warmup resolves `none`; the journal names the source in every case. *(probe C0/C3 sections)*
- [x] **C4:** artifacts: the index lists versions; `../` traversal and foreign paths are refused; another run's artifact is 404; another app's run is 403. *(probe C4)*

## Risks

- **In-process run failure:** `WorkflowRunError` is contained and journaled as a real run; the server survives `unhandledRejection`, launchd KeepAlive is the backstop, and budgets + heartbeat `lastEventAgeMs` make a hung run visible.
- **Event-loop contention:** runs are async I/O; the proxy hot path is unaffected; per-run costs are bounded by the existing caps.
- **Token blast radius:** apps are explicit roster rows; a leaked app token is bounded by its ceiling — which is the point of ceilings.

## Incident record (recorded honestly)

The probe's first version ran a full `kit apply`. The apply pipeline's service step re-registered the launchd label `com.agnostic-router.model-router` — the **live zcode-router-kit edition's** service (8300) — against the scratch home, so launchd was briefly keeping the scratch server alive and the label pointed at a `/tmp` path that probe cleanup would have deleted. Repaired in session: the label was booted out, the plist restored to `~/.zcode/router/server.js` (working dir, logs, KeepAlive, RunAtLoad), the orphaned pre-incident router process retired, and launchd respawned the live router under the restored service (verified: PPID 1, `/healthz` green, runtime config byte-untouched). The probe now runs `apply --only router` — it never touches launchd — and treats the rendered runtime files, not apply's exit code, as its success criterion (apply's final health check waits for a server the probe starts afterward).

## Notes

- **sys1 decision-shape check:** spawn validation, ceiling enforcement, sandboxing and answer resolution are deterministic code — no sys1 head fits and none is added. Judgments inside spawned runs keep routing dev-decisions first per the C6 law; the API is a caller layer, not a judgment layer.
- Naming: the plane is the control plane for agent work; this makes spawn itself a declared, gated, journaled capability — the wire the control plane deserved from the start.
- Roadmap tie-in recorded in the feature doc: the second-brain tower can later consume this wire (disposition buttons on app runs); an AG-UI render is the face. Neither is built here.
